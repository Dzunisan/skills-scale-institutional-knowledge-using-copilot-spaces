# OctoAcme Project Management Docs

This folder holds the project management processes used by OctoAcme. Start here to find the right guide.

## Summary of the project management processes

OctoAcme runs projects in small, testable steps. Work starts with **project initiation**: the team writes a one-pager, names the stakeholders, sets success metrics, and makes a go/no-go decision. In **project planning**, the approved work becomes a prioritized backlog with acceptance criteria, estimates, a Definition of Done, and a release plan with milestones.

During **execution and tracking**, the team uses a project board, daily standups, a weekly delivery sync, and demos at the end of each sprint. Changes go through small pull requests that link to an issue, pass CI and security scans, and get at least one approval before merge.

Each project has clear **roles**: a Project Manager coordinates delivery, risk, and communication; a Product Manager owns outcomes and the backlog; Developers build and test; QA checks quality; Stakeholders give input and approval. **Risks** are kept in a simple risk register and reviewed every week. Stakeholders get regular updates from one source of truth.

**Quality** is protected by tests, CI checks, and a release checklist. Each **release** has release notes, a rollback plan, and smoke tests in staging before production. After each sprint, release, or incident, the team runs a **retrospective** and turns the top 2–3 lessons into backlog items with owners.
